## Why I built it

This was a group presentation for my high school linear algebra class. We wanted to show a place where matrices do real work, and robots are a good example: a robot has to know where it is, but every sensor it has is a little wrong.

## How it works

### The problem: sensors lie a little

Robots usually measure their own motion in two ways, and each has a weak spot.

- **Wheel encoders** count how far the wheels turn. They are precise, but they assume the wheels grip the floor. If a wheel spins on carpet, the encoder can report 2 m of travel while the robot has not moved at all.
- **An IMU** (a tiny motion-sensor chip) measures force and acceleration. It is fast, but small errors add up, so its position estimate drifts over time.

A Kalman filter does not trust any one source. It keeps a best guess and keeps correcting it.

### The idea: predict, then correct

The filter tracks a **state**: the robot's position and velocity, stored as a 2 by 1 vector. Every time step does the same two things.

1. **Predict.** Use physics to guess the next state. For straight-line motion, new position = old position + velocity × time. In matrix form that is one multiply, the new state is `A` times the old state. The filter also makes itself a little less sure of the guess, because real robots do things the model does not expect.
2. **Correct.** A sensor reading arrives. The filter compares it with what it expected the sensor to read. That difference is called the **innovation**. The filter moves its guess part of the way toward the reading.

How far it moves is set by the **Kalman gain**, `K`. Think of it as a balance between two kinds of doubt: how unsure the filter is about its own prediction, and how noisy the sensor is. In one dimension it works out to roughly

`K = prediction doubt / (prediction doubt + sensor noise)`

- If the sensor is very noisy, `K` goes toward 0 and the filter trusts the physics.
- If the prediction is very unsure, `K` goes toward 1 and the filter trusts the sensor.

### The matrices

| Matrix | What it is | In my demo |
|---|---|---|
| `A` | Moves the state forward one step using physics | `[1 0.1; 0 1]`: position grows by velocity × 0.1 s, velocity stays the same |
| `H` | Turns the state into what the sensor sees | `[1 0]`: the sensor reads position only |
| `Q` | How much the real robot can surprise the model | `0.1` on position and velocity |
| `R` | How noisy the sensor is | `10`, a standard deviation of about 3.2 m |
| `P` | How unsure the filter is about its current guess | Starts as the identity matrix and updates every step |
| `K` | The Kalman gain, recomputed every step from `P` and `R` | Settles near 0.16 (see Results) |

### Why everything has to be linear

The standard Kalman filter only works when the system is linear, meaning doubling an input doubles the output and adding two inputs adds their outputs. That is why the physics goes in a matrix with no squared terms like t² and no sine or cosine. The filter also assumes the sensor noise follows a bell curve (a normal distribution), which is what lets it describe uncertainty with covariance matrices like `P`, `Q` and `R`.

### My MATLAB demo

To show the filter working, my script simulates a robot that starts at rest and speeds up at 1 m/s² for 10 seconds, so its true position is 0.5t². The fake sensor reports that position plus random noise. This is the filter loop:

```matlab
for i = 1:length(time)
    % Predict
    x_pred = A * x;
    P_pred = A * P * A' + Q;

    % Correct
    K = P_pred * H' / (H * P_pred * H' + R);
    x = x_pred + K * (noisy_data(i) - H * x_pred);
    P = (eye(2) - K * H) * P_pred;

    filtered_estimate(i) = x(1);
end
```

## What went wrong and what I optimized

The filter's estimate runs a little behind the true position. The model assumes the velocity stays the same, but the simulated robot keeps speeding up, so the filter is always catching up. In the last 3 seconds of the run below, the estimate is about 1.1 m behind on average. Across 200 runs it is about 1.0 m behind.

Even with that lag, the filter cuts the error by more than half compared with reading the sensor directly.
